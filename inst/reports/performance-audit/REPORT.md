# PDRobust data-processing performance and compatibility audit

The principal scalability defect was subject-name lookup inside the longitudinal-completeness loop. Its cost grows approximately quadratically with the number of subjects. The implemented changes remove that loop for ordinary IDs, replace other subject loops with grouped operations, and preserve the complete validation contract. No prediction, diagnostic, HTE, model-fitting, simulation, public interface, or rounding code was changed.

## Measured results and concise function report

**At N=30,000/K=3 (90,000 rows), the median speedups are 23.1× for `DataCheck()` and 22.6× for `DataStandard()`.** These timings are from the final sequential run, with no concurrent audit test jobs.

| Function | Original bottleneck / action | Original → optimized elapsed | Approximate R-heap high-water, original → optimized | Compatibility risk |
|---|---|---:|---:|---|
| `Mapping()` | Metadata only; unchanged | 0–1 ms after warmup; no meaningful change | Negligible operation increment after warmup; mapping remains 2.9 KiB | None introduced |
| `DataCheck()` | Quadratic named subject lookups and repeated subject scans; grouped counts, binary flags and stable survival ordering implemented | **15.564 → 0.675 s (23.1×)** | **135.2 → 101.1 MiB (25.2% lower)** | Low, with exact old/new comparisons and legacy fallbacks; no validation removed |
| `DataStandard()` | Two costly checks plus per-subject covariate data frames; inherits checker improvements and groups row-missingness flags | **37.047 → 1.641 s (22.6×)** | **135.9 → 115.2 MiB (15.2% lower)** | Low; both full checks, sorting, values, types and audit attributes retained |

The heap column is an indicator derived from R's separately recorded heap maxima, **not exact peak process RSS**. Output sizes are unchanged: at N=100,000 the raw input is 29.76 MiB and the standardized object is 36.30 MiB, including the ID audit map. Memory improvement is not universal: at N=3,000 the standardizer's heap indicator increased from 83.3 to 90.6 MiB. Allocation-volume results and their limitations are discussed below.

The warmed allocation profile at N=3,000 recorded **12.38 → 13.79 MiB for checking (+11.5%)** and **31.82 → 35.47 MiB for standardization (+11.5%)** in byte-counted allocations. Small-object page events fell from 2,578 to 0 for checking and from 2,587 to 392 for standardization, but their unreported byte sizes and allocator reuse prevent converting those event counts into a net allocation saving. The implementation trades many subject-level objects for fewer larger vectors; measured lower heap high-water at N=30,000 and higher recorded allocation volume at N=3,000 are compatible findings. No claim of reduced total allocation volume is made.

The first small-size results are subject to compilation/timer noise. The informative larger-size comparison is that tripling N from 10,000 to 30,000 multiplies original checker time by 8.0, while the optimized checker and standardizer grow almost proportionally to rows over 10,000–100,000 subjects.

The warmed N=10,000 CPU profile attributes about **56%** of original checker samples to the two named-lookup lines (`baseline/data_validation.R:321–322`), with another **21%** in subject-wise survival checks. Within original standardization, the two checkers account for about **74%** and the subject-wise model-data check for **22%**. After optimization, `table()`/frequency sorting in the variation helper accounts for about **42%** of both operations; key construction and factor levels are other visible residual costs. These percentages are sampled attribution, not isolated-kernel benchmark times. Mapping's first timed call included about 42 ms of compilation in both versions; later calls are around the timer's 0–1 ms resolution.

**Million-subject extrapolation, not a benchmark:** applying N² scaling to the original N=30,000 times gives approximately **5 hours per check and 11 hours per standardization** on this machine. Applying linear scaling to the optimized N=100,000 times gives approximately **23 seconds and 53 seconds**, respectively. These simple projections show the change in dominant cost; they are not HPC forecasts or runtime guarantees. Character-ID sorting, larger strings/hash tables, covariate cardinality and allocator pressure can make the optimized result slower than linear projection. At N=100,000, the optimized incremental heap indicators are 130.2 MiB/check and 181.3 MiB/standardization. A linear memory projection is roughly 1.3/1.8 GiB of additional R heap at N=1M, with considerable uncertainty; it does not measure native memory, simultaneous peak RSS or downstream fitting. The raw/standardized payload alone would be roughly 298/363 MiB.

**Verification:** 535 package assertions passed, with zero failures, errors, warnings or skips. There were 2,008 exact old/new comparisons, additional generator comparisons for both outcomes and K=1/3/6, and ten successful full-precision prediction/HTE comparisons before public rounding. No million-subject execution was required.

## Source and scope

The audit uses the working source present on 12 September 2026. The requested version was 0.3.7, but `DESCRIPTION` reported **0.3.8**; HEAD `5b7750336b4d005138dab6c2dd17dab86604d9d2` reported **0.3.7.2**. The pre-existing differences in `Mapping.R` and `data_validation.R` relative to HEAD were documentation changes. This is an audit of the current working implementation, not a claim to have tested an independently installed 0.3.7 release. Existing user edits were preserved.

`baseline/` preserves the exact pre-audit implementations of the three public functions, their data-validation and utility helpers, and the current development generator. `baseline-sha256.txt` records their hashes. The benchmark sources these files into an isolated environment; it does not accidentally benchmark an installed package. The edited production code is entirely in `R/data_validation.R`, with regression tests in `tests/testthat/test-data-scalability.R`.

The benchmark generator is extracted from `data-raw/generate_example_data.R` without executing that script's data-rebuild commands. The embedded `generate_data_example()` in `01_reference_beta_N1M.R` was also inspected; its output matched the development generator at the same N=100, K=3 and seed. The reference script specifies K=3 and six baseline covariates. Simulations therefore use **R = N × K = 3N rows**, six covariates, and all 16 returned columns, including unused potential-outcome columns. The generator returns a `data.table`, rounds designated returned double columns to three decimals, and leaves outcomes structurally missing after death. None of these behaviors was altered.

## Execution paths and downstream contracts

**Mapping.** `Mapping()` validates five scalar structural names and their distinctness; validates/deduplicates covariate and interest-variable names; rejects structural overlap and interest variables absent from covariates; validates finite ordered endpoints; normalizes and validates outcome type; returns the same `pd_mapping` list. `.pd_stop()` supplies errors. Printing uses `.pd_time_label()`. `.pd_validate_mapping()` subsequently checks class, required fields and the prohibition on `target_time`; it deliberately does not reconstruct the mapping or repeat all constructor validation. No data are passed to any of these operations. Runtime/memory depend on the number of variable names, not N.

**DataCheck.** The public wrapper calls `.pd_check_data_impl()` and then `.pd_round_data_check()`. The implementation validates mapping and `strict`, normalizes the input through `.pd_as_data_frame()`, checks columns/nonempty input with early returns, records missing identifiers, converts time, checks endpoints and constructs the actual observed analysis grid. It then checks duplicate ID/time keys and visit completeness, treatment and survival encoding, within-subject treatment constancy and survival history, outcome encoding, post-death and survivor outcome missingness, covariate missingness, ordering/time/ID coding, baseline treatment availability, and near-zero covariate variation. It assembles checks/diagnostics and readiness flags before applying `strict`. Helper functions are `.pd_key()`, `.pd_numeric_conversion()`, `.pd_binary_conversion()`, `.pd_display_values()`, `.pd_is_consecutive_integer_id()`, `.pd_near_zero_variation()`, `.pd_time_label()`, and `.pd_stop()`. New private helpers implement grouped visit counts and survival transitions. Return-boundary rounding only touches diagnostic percentages; identifiers, indices, counts and times retain their types and values.

**DataStandard.** `.pd_standardize_data_impl()` validates `drop`, runs the **full initial checker**, normalizes the input again, and stops for manual-resolution failures. It repeats explicit mapped-column conversions, records original rows/IDs, conditionally removes unidentifiable rows, removes rows outside the mapped window, and recomputes the retained observed time grid. It identifies subjects with missing visits or required analysis values; preserves the existing reason order; rejects deletion without `drop=TRUE`; and otherwise removes whole subjects. It constructs the time audit map, maps time to consecutive integers starting at zero, builds ID levels using the original ID's sorting semantics, assigns integer IDs, reconverts structural storage types, creates a standardized mapping with `Mapping()`, sorts by standardized ID/time, and clears row names. It runs the **full final checker**, builds attrition, attaches mapping/original mapping/check/standardization attributes, and emits the existing warning if final readiness fails. The public wrapper rounds only display diagnostics and attrition percentages. Both checker passes and all public attributes remain.

The conversion helpers themselves scan vectors. `.pd_numeric_conversion()` converts to double, rejects nonmissing nonfinite/unparseable values, and suppresses coercion warnings while recording invalid rows. `.pd_binary_conversion()` accepts numeric 0/1, logical encodings and explicit character/factor "0"/"1" labels, with different canonical flags; ambiguous labels remain invalid. `.pd_display_values()` computes unique nonmissing values before limiting their display. `.pd_is_consecutive_integer_id()` sorts distinct numeric values and uses `all.equal()` against a numeric sequence. `.pd_as_data_frame()` dispatches `as.data.frame()`, preserves mapping/readiness attributes and restores `pd_data` when applicable. `.pd_round_output()` restores attributes after rounding display-only doubles; `%||%` resolves optional fields, while `.pd_stop()` and `.pd_warn()` preserve condition messages. None of these helper definitions changed.

**Prediction, diagnostics and HTE depend on these contracts.** `.pd_require_prepared_data()` checks the `pd_data` class and attached readiness result; `.pd_mapping_for_data()` retrieves the structural roles. `.pd_analysis_times()` requires every standardized observed visit from baseline through cutoff. `PSPred()` selects one baseline row per subject, validates the treatment response and fits a GLM. `PrinPred()` independently checks duplicate pairs and complete prediction panels, sorts histories, constructs risk sets from the preceding visit, fits a survival GLM, and computes within-subject cumulative products before restoring prediction order. `OutPred()` uses nonmissing outcomes and the mapped outcome type to choose its model. Their model helpers also construct model frames/design matrices and diagnostics.

`HTEAllT()` and `HTESepT()` use `.pd_prepare_hte()`, `.pd_hte_components()`, `.pd_align_time_rows()`, `.pd_hte_weights()` and outcome helpers. Baseline, cutoff and current-time rows must align by ID; effect modifiers must remain numeric; principal scores must describe cumulative survival across the full grid; structural outcome missingness must remain intact. Full-precision values feed the estimators; rounding occurs at their public return boundaries. `PSDiag()`, `PrinSDiag()`, `ORCI()`, `QR()` and `SA()` also consume these mappings, visits, scores or prepared-data contracts. Faster preprocessing does not remove the independent per-subject loops in `PrinPred()`, model-matrix costs, HTE population copies or repeated bootstrap fits. Those implementations are outside this change.

## Bottleneck inventory

Here N is the number of subjects, R the number of longitudinal rows, K the number of required visits, P the number of mapped covariates, W the number of all retained columns, and U a variable's distinct-value count. Sorting bounds are conservative: base R's automatic radix paths often make integer/numeric sorting close to linear.

| Current/pre-audit operation | Approximate cost and practical significance | Disposition |
|---|---|---|
| `Mapping()` name validation, `unique`, `intersect`, `setdiff` | O(P) expected time/storage for short metadata vectors; independent of N. Not a large-data bottleneck. | Unchanged. |
| `split(valid_id_rows, character_id)` plus `id_groups[[subject]]` and `complete_subject[[subject]]` in the completeness loop | Character-name searches inside N iterations can scan O(N) names each: **O(N² + R)** overall, with an O(R+N) split list and many small subject vectors. This is the dominant measured defect, not a theoretical concern. | Replaced on ordinary IDs by factor group codes and visit counts. Empty-string-ID legacy path retained. |
| Missing-by-time nested `vapply` and per-subject `unique` | O(KR + NK) work/calls on short histories; millions of R function calls even for K=3. | Count distinct group/visit pairs once. Reuse the existing duplicate-pair result to avoid an unnecessary sort on clean input. |
| Treatment `unique(na.omit(A[idx]))` per subject | O(R+N) element work but N calls and small temporary objects. Material after the quadratic defect is removed. | Two group tabulations detect the presence of both 0 and 1; NA remains ignored. |
| Survival `order`, `na.omit`, `diff` per subject | O(sum K_i log K_i), with N sorting calls and temporaries. At short K, call overhead dominates. | One stable group/time ordering and adjacent comparisons within groups; temporary vectors remain local to a helper. |
| Standardizer's subject-wise missingness check and `data[idx, covariates]` | O(RP + NP) element/object work, with N small data frames and short-circuit scans. A major practical cost; no statistical model is involved. | One complete-cases pass and group flags for ordinary unclassed logical/integer/double/character covariates. Exact legacy path retained for other column types. |
| `paste(character_ID, numeric_time, sep="\r")`, two `duplicated` passes | Expected O(R) hashing/string construction, O(R) strings, pointer vectors and hash tables. Millions of distinct keys are expensive even though complexity is linear. All duplicate row indices, including first occurrences, must be reported. | Preserved; its result is reused. |
| Repeated conversions, ID keys, `unique` and `sort` | O(R) scans/conversions; numeric-ID distinct sorting up to O(N log N), observed-time sorting O(K log K). Character/factor encodings add large vectors. The standardizer includes two checkers plus its own conversions. Material but smaller than the original loops. | Reused the identical complete-row index and in-window time vector within each check; retained encoding and ID semantics elsewhere. |
| Near-zero variation: `na.omit`, `table`, descending `sort` for every covariate | At least O(PR) scans; level construction and count sorting up to O(P(R log R + U log U)); O(R+U) temporaries per variable. Numeric level formatting makes this a remaining practical CPU cost. The generator's three-decimal rounding limits U substantially, so extrapolation to unrounded continuous covariates is inappropriate. | Preserved, including factor-level and numerical-grouping behavior. |
| Covariate/survivor missingness scans and diagnostic strings | O(PR), plus O(K × missing-survivor-rows). Normally modest at six covariates/three visits; invalid million-subject data can create enormous row/ID strings and diagnostic vectors. | Preserved. Detailed errors are observable behavior. |
| Repeated data-frame conversion, window/deletion subsets and final sorting | Coercion cost is class-dependent; `data.table` to `data.frame` can copy columns. Row subsets materialize O(RW) column storage. Sorting adds index arrays and another O(RW) output; extra unused columns increase all subset costs. R copy-on-modify means not every assignment is a deep copy. | Preserved. No new matrix or `data.table` conversion was introduced. |
| Two checks within standardization; optional separate public `DataCheck` | `DataStandard` costs two full validations plus its transformations. A user calling `DataCheck` first incurs three checks in the workflow; no validation cache exists. | Both internal checks retained. A separate preliminary check is useful for inspection but is not required before calling `DataStandard`. |
| Attributes, attrition and public rounding | Successful checks are small; ID audit maps are O(N), time maps O(K), and detailed failures can be O(R). Percentage rounding is only O(P), not a scan over the full dataset. | Preserved; no benefit from changing public rounding. |

There is no matrix conversion inside the audited data-validation implementation. The generator constructs matrices, and downstream statistical functions construct design/effect-modifier matrices; those costs should not be misattributed to `Mapping()` or the checker.

## Implemented changes and equivalence argument

The grouping representation uses `factor()` on the same character ID keys used by `split()`. Its levels preserve split's locale-dependent group ordering. Completeness diagnostics are assigned back in original ID encounter order, while treatment/survival diagnostic IDs and deletion reasons retain their original group order. Missing keys remain excluded from groups.

Visit completeness is still the predicate “every required observed time is present.” Duplicate pairs are collapsed for counting when present, while the unchanged duplicate check still reports them as fatal. When the duplicate check has already established unique pairs, simple row counts are equivalent; standardization's initial manual-resolution gate guarantees this before its own row filtering. No floating-point pair packing, string-to-numeric ID equivalence changes, or dense N-by-K matrix is used.

For successfully converted binary treatment, more than one nonmissing value means precisely that both zero and one occur. For binary survival, an increase in the nonmissing ordered sequence means an adjacent zero-to-one transition. Filtering missing survival before a stable time sort gives the same remaining sequence as sorting and then omitting missing survival. Ties retain original row order, missing times sort last, and comparisons never cross subject boundaries. History checks still include rows outside the mapped window.

For plain supported covariate vectors, “any missing required value in a subject” equals grouping row-level missingness flags. The whole-column operation does not alter those values. Classed, named, matrix, raw, complex and list columns retain the former per-subject path because their subsetting/complete-cases or error behavior may differ. Empty-string IDs retain their existing completeness anomaly rather than silently receiving a bug fix. These fallbacks prioritize compatibility over universal speed.

## Risky proposals: not implemented

**1. Trust a saved readiness flag or remove the initial/final checker.** The cost is repeated full validation and conversion. Reusing cached results or declaring transformed data ready could remove roughly one checker per eliminated pass; removing the final pass could approach half of the remaining standardization validation cost. Peak savings depend on overlapping live objects and cannot be equated to half the process memory. Data frames and mappings can be modified after a check, and deletion can change treatment availability or covariate variation. Accepted inputs, error precedence, diagnostics and readiness attributes could therefore change. All prepared-data consumers, especially HTE and diagnostic entry points that trust the attached check, would be affected. **Not recommended** without an explicit cache-invalidation and equivalence design; both passes remain.

**2. Validate only retained visits, only survivors, or baseline covariates.** The current checker scans all supplied rows and all mapped covariates, including outside-window histories. Restricting checks to a subset could reduce column-work roughly in proportion to retained rows; baseline-only covariate work is about K-fold smaller for this generator. In general, covariates can vary over time, and off-window duplicate records, inconsistent treatment/survival, invalid encodings or missing values currently cause diagnostics or errors. The change could admit data currently rejected, alter attrition, and alter the sample for PS, principal/outcome prediction, all HTE estimators and diagnostics. **Not recommended** as an implicit optimization. The generator's repeated baseline covariates do not establish a public-input invariant.

**3. Replace the existing pasted duplicate keys with exact pair hashes or integer combinations.** The cost is an O(R) vector of concatenated keys and its hash tables. Integer pair handling could avoid millions of string objects and save roughly hundreds of MiB at three million distinct short keys, with runtime savings on string construction/hashing. However, the existing key uses character formatting of numeric time and IDs. Close floating-point times, unusual ID representations and separators can therefore have legacy equality behavior different from exact pairs; integer arithmetic can additionally overflow if designed carelessly. Which rows are diagnosed as duplicates and which inputs reach analysis could change. `PrinPred()` independently uses pasted keys, so inconsistent definitions could break it and every HTE/diagnostic consumer of principal scores. **Recommend a separate equality-contract review**, not an automatic replacement. Current key construction and duplicate diagnostics remain exact.

**4. Replace `table()` variation diagnostics with numeric hashing, sampling or baseline-only counts.** The cost is repeated frequency construction and sorting, especially on unrounded high-cardinality covariates. Numeric hashing or sampling could eliminate substantial formatting/sorting work; its maximum whole-function benefit is limited to the measured variation-diagnostic share. Base `table()` retains factor-level conventions and has numeric level-construction semantics that a simple `unique`/`tabulate` rewrite need not reproduce. Sampling can miss rare levels and changes reproducibility. Near-zero-variation warnings, diagnostic names and percentages could change; removing covariates in response would then affect PS/principal/outcome models, HTE and profiling. **Do not change the definition or sample it.** A future implementation may optimize the exact existing frequency result if it proves equality for these cases; only removing the final short count sort would offer limited benefit on the rounded generator.

**5. Use by-reference `data.table` updates/sorting, or discard unused columns.** The current class normalization and row subsets can copy O(RW) values. By-reference operations or narrower data can remove a substantial fraction of those copies. At N=1M/K=3 the generator's 16-column raw payload alone is approximately 298 MiB; one avoided whole-frame materialization is therefore meaningful. Direct updates could mutate the caller's object, alter row names/classes/custom attributes, or reorder aliases of the input. Dropping unused columns changes returned values and can remove variables needed by later analyses or user code. All downstream functions and reproducibility checks could be affected. **Not recommended on user-owned data.** A private-copy implementation may be safe after class/attribute testing, but its copy cost and dependency implications must be measured first. No such change was made.

**6. Truncate diagnostic IDs/row indices, omit audit maps, or stop at the first failure.** Current reports retain full row and ID details, the original and final checks, the ID/time audit maps and detailed deletion reasons. Capping details or returning less information would save O(number of failures) storage and potentially long string-building times; eliminating the ID map saves O(N) even on clean input. It would change returned attributes, error text/order and diagnostic coverage. Direct model calculations may not use every audit field, but mapping provenance, `drop=TRUE` review and users' downstream audit code would be affected. **Not recommended without a separately specified public reporting option.** All existing details remain.

**7. Parallelize/rewrite downstream cumulative products or change numeric precision.** `PrinPred()` still splits/sorts subjects and computes cumulative products; HTE fits models and may bootstrap repeatedly. Those stages may dominate after this audit's improvements. Parallel loops or alternate matrix kernels could help, but changing multiplication/fit/reduction order, BLAS behavior, RNG streams or precision can alter results and reproducibility. Expected runtime/memory gains are **unquantified here**: those functions were exercised for equivalence on small data, not benchmarked at scale. A million-subject end-to-end HTE speedup cannot be inferred from preprocessing timings. `PrinPred`, `HTEAllT`, `HTESepT`, `PrinSDiag`, `QR` and `SA` would need dedicated comparisons. **Recommend a separate downstream audit** that preserves full precision and seed behavior; no prediction/statistical changes are included here.

**8. Skip ID/time remapping or strengthen canonical-ID tests.** The cost is repeated `unique`, ordering, `match`, audit-map construction and mapped-column allocation. Assuming IDs are already consecutive could save O(R+N) work and integer index storage. However, the current canonical-ID helper uses tolerant `all.equal()`, and original-ID sorting follows the input type (including factor levels). A strict integer test changes readiness for nearly integral IDs; bypassing remapping based on the existing tolerant flag can leave noninteger storage/values or change raw-ID audit ordering. Time remapping must retain the full actual observed grid, not merely endpoint spacing. Returned IDs, time maps, classes and validation flags could change, with consequences for every ID-aligned PS/principal/outcome and HTE calculation. **Not recommended based only on the current flag.** An exact precondition and complete audit-map equivalence would be required; expected gains are secondary to the subject-loop fixes.

## Measurement and verification

Benchmarks use R 4.4.3 on macOS x86_64, a fixed generator seed (20260912), one data.table thread, K=3 and six mapped/effect-modifier covariates. Generation is outside timed expressions. Reported elapsed times are medians of three calls with garbage collection between calls; the earliest small run may include compilation. These are shared-desktop measurements, not controlled HPC measurements or confidence intervals. Verification work overlapped some exploratory measurements; the final timings/profiles and raw CSVs document what was run. The user’s Great Lakes R 4.6.0 environment was not benchmarked.

`gc(reset=TRUE)` supplies an approximate R-heap high-water indicator by summing node-heap and vector-heap maxima. Those maxima need not occur simultaneously; this is **not exact peak RSS** and excludes untracked native allocations. Incremental values subtract the live heap at entry. GC thresholds and retained capacity can make small cases nonmonotone. `Rprofmem` separately records allocation volume, not peak live memory; byte-counted records exclude unquantified small-object page events. Do not interpret fewer per-subject objects as proof of lower allocation volume or universally lower peak memory. R profiles use 10-ms sampling, with warmup outside profiling; N=3,000 allocation profiles have threshold zero and N=10,000 profiles record allocations above 1,000 bytes. Small percentages are approximate.

The benchmark stops at N=30,000 for the original implementation and N=100,000 for the optimized implementation. No million-subject input or million-subject model fit was run. The original quadratic lookup is already established by source inspection and scaling; running it at N=1M solely to confirm this would be unnecessarily expensive.

Verification compares complete `DataCheck()` and `DataStandard()` objects with `identical()`, including all columns, storage modes, classes, row names/order, mapping/original mapping, audit maps, attrition and checks. It checks input immutability, warning/message/error classes and text, strict/drop behavior, empty/missing columns, supported and unsupported encodings, shuffled/missing/duplicate visits, invalid/out-of-window histories, empty/factor/date IDs, classed/matrix/list covariates, and deterministic malformed-panel cases. Additional generator comparisons cover continuous/binary outcomes, K=1/3/6, N up to 10,000, all 16 columns, shuffled rows and noninteger/narrowed time windows. Processing leaves RNG state unchanged.

Downstream comparisons run PS, principal and outcome prediction, both HTE estimators at B=0 with multiple `HTESepT` target times, and balance/profiling diagnostics on the old/new prepared data. Numerical outputs, diagnostic data, warnings and RNG state agree. Independently generated plot environments and GLM-family closure environments are excluded from identity comparisons; plot data and closure definitions are compared instead. All prepared-data attributes themselves are compared without exclusions. A separate `full-precision-compare.R` script confirms exact identity of unrounded internal PS/principal/outcome predictions and both HTE estimating results for continuous and binary outcomes (ten successful cases). Existing package tests additionally exercise bootstrap, row alignment, rounding, warning policy and restored algorithms. This is regression evidence and an equivalence argument, not a proof for every arbitrary user-defined R method or platform. The full testthat suite was run; a separate `R CMD check` was not run.

To reproduce from the package root, run `Rscript inst/reports/performance-audit/compare.R`, `Rscript inst/reports/performance-audit/generated-compare.R`, `Rscript inst/reports/performance-audit/full-precision-compare.R`, and the package's `testthat::test_local()`. Run `Rscript inst/reports/performance-audit/benchmark.R old 1000 3000 10000 30000` and the same script with `new 1000 3000 10000 30000 100000` for timing. For profiling, set `PD_AUDIT_PROFILE=1`; set `PD_AUDIT_ALLOCATION_MIN_BYTES=0` for the N=3,000 full allocation profile. Three calls warm the relevant paths before profiling. `summarize.R` builds compact CSV and CPU summaries. Full profiles, test summaries, comparison logs and session information accompany this report. These development artifacts live under the already build-ignored `inst/reports/` directory.

The new vectorized paths have O(R+N) temporary storage rather than a subject list plus many small temporaries. This is not a guarantee of lower live memory for every R/N ratio: very long histories can make full-row ordering vectors more expensive than short per-subject working vectors. The measured memory comparison applies to the requested generator with K=3, and should not be generalized to arbitrary wide or very long panels.
